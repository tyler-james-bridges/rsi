# Observer v1 data classification and retention

## Rules that apply to every class

1. Data is hostile until explicitly classified and admitted by a closed runtime
   schema. Unknown data is rejected, not stored “just in case.”
2. Retention is a maximum, not a minimum. A shorter lifetime is preferred when the
   work is complete.
3. “Session close” includes successful close, abort, timeout, crash recovery, and
   orphan cleanup. Failure to destroy required data stops and invalidates work.
4. Backup, model, event, dashboard, and publication permission are independent. A
   value allowed in one is not implied to be allowed in another.
5. Qualification has no raw-data forensics exception. Reproduce failures with
   synthetic or licensed fixtures after preserving only permitted typed errors.

## Classification levels

| Class            | Meaning                                                                       | Default handling                                                          |
| ---------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `D0-PUBLIC`      | Reviewed, signed, content-free public material                                | Publish only through MacBook approval and correction chain                |
| `D1-GOVERNANCE`  | Sanitized signed operational, release, feedback, and policy evidence          | Private durable, backed up and integrity-linked                           |
| `D2-VOLATILE`    | Typed private market/source observations needed briefly                       | Encrypted/private, short TTL, no public output                            |
| `D3-HOSTILE-RAW` | Exact provider bytes, identifiers, metadata, and hostile text                 | Per-capture encrypted, quarantine-only, session-close destruction         |
| `D4-SECRET`      | Credentials, keys, recovery material, private endpoints                       | Keychain/offline custody only; never events, logs, chat, or project files |
| `D5-FORBIDDEN`   | Financial credentials/capabilities, NFT media/metadata, unclassified raw data | Do not acquire in Observer v1                                             |

## `ModelObservationV1` negative schema

The model input schema MUST reject, rather than redact after serialization:

- raw text, quote fragments, HTML, media, OCR, and arbitrary user-controlled prose;
- X/Post/user IDs, account names, handles, URLs, queries, provider names/origins,
  and source-response hashes or fingerprints;
- vault capture IDs, snapshot addresses, cursor values, and storage paths;
- credentials, secrets, email addresses, account/card data, wallet or RPC secrets;
- unbounded error text, stack traces, and host/network details;
- executable instructions, calldata, tool names, manifests, or spend requests.

Allowed fields are bounded numeric features and enums, coarse time/freshness
buckets, evidence levels, policy reason codes, costs, latency, abstention state,
exact independently verified onchain asset identity, and opaque ephemeral
references. Exact order, source, provider, account, Post/User/edit-history, query,
and capture identifiers are not model input. Private free-form feedback notes are
also excluded.

## Permanent event allowlist

Production events MUST use closed versioned schemas. The common envelope is limited
to:

- schema version, random event/aggregate/session identifiers, environment, event
  type, sequence, predecessor, timestamp, and idempotency key;
- permitted release/config/policy/checkpoint hashes;
- permitted parsed sanitized-model-result hashes with bounded
  model/schema/usage/cost audit;
- bounded enums, counts, costs, freshness, lane status, cursor status without value,
  deletion/backup/anchor status, and incident class/code;
- exact approved onchain/order identifiers only when the event is a verified
  canonical fact and not a public artifact;
- signed feedback, StrategyPatch, promotion, correction, activation, and retirement
  references.

Any other field is rejected. A generic “metadata,” “details,” “message,” “raw,” or
open-ended extension object is forbidden.

## Deletion protocol

For every capture, purge MUST be idempotent and demonstrate:

1. the capture transitioned to a deletion-pending state;
2. its per-capture DEK was destroyed;
3. encrypted body, metadata, and identifier-index entries were removed;
4. expiry/orphan scans found no reachable or unindexed remnants;
5. only a content-free receipt containing random ID, time, class, count/bytes,
   success status, and permitted integrity reference entered the event log;
6. retrying purge cannot resurrect or duplicate semantic data.

If any step cannot be demonstrated, collection stops, the session invalidates, and
the Class B/C analysis in the incident taxonomy applies. No operator control may
convert failed deletion into longer retention.

## Retirement

Retirement disables scheduling and egress, revokes provider credentials, destroys
operations-state and vault-wrapping keys and cursors, purges ephemeral data, and
writes a signed final checkpoint. Sanitized governance records remain only for
their approved 365-day period and any unavoidable B2 retention lock, then are
crypto-shredded unless a legal requirement explicitly applies. The public surface
retains only a signed content-free retired status and its correction chain.
